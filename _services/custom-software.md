## Start with the work your software needs to support

You copy orders between systems, reconcile spreadsheets or ask colleagues which record is current. Customers, payments and tasks sit in separate tools. A new dashboard alone will not resolve an unclear handoff.

Monte del Gallo builds custom software for operations teams that need a shared workflow and founders developing a product. We start with the people doing the work: what they enter, what they need to see and what happens when something goes wrong.

Bring an existing application or a process you still run by hand. You do not need a finished specification to discuss it.

## Internal tools, SaaS products and integrations

We define the application around its users and the decisions they need to make.

- **Internal tools:** operational platforms for orders, customers, properties or administrative work, with relevant views and reporting.
- **SaaS products:** applications with accounts, user roles and workflows for customers, including payments where the product needs them.
- **Integrations:** connections between the application and existing systems, so your staff can work from shared information rather than re-entering it.

We also assess existing software. Extending a working application or replacing a troublesome component may fit better than rebuilding the whole system. Data imports, exports and migration need their own scope alongside new features.

## When custom development makes sense

Custom software is worth considering when your workflow needs rules that off-the-shelf tools cannot accommodate, or when you are building a product for customers. You need someone on your side who can explain priorities and review the work with us.

If an existing product handles the essential process, configuring it may be the better investment. If responsibilities or data sources remain unclear, resolve those questions before commissioning a large application.

This service starts with the project, not a framework. If your main requirement is continuity with an existing stack, see [Ruby on Rails development](/services/ruby-on-rails-development/). For a web interface connected to an existing backend, see [React and JavaScript development](/services/react-javascript-development/).

## Define the scope, review the work, plan the release

We map the current workflow, data and dependencies with you. We then agree on the initial scope, what sits outside it and how you will check that the software supports the intended task.

During development, we review working flows together and use feedback to decide what to change next. Before release, we agree on checks, data transfer needs and how people will start using the application.

The proposal defines the deliverables: application features, integrations, documentation and handover where required. We discuss maintenance and later changes as part of the engagement. Scope and dependencies shape the delivery plan; a generic deadline would hide those decisions.
