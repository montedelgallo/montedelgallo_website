# Cloudflare Pages: how the site is deployed

The site is **built by GitHub Actions** and uploaded to Cloudflare Pages as a **Direct Upload**.
Pages never builds it: the site needs Ruby, the Jekyll plugins and jekyll-polyglot, which Pages'
own build image does not run. The folder that is uploaded is exactly the `_site` that the `build`
job has just built (`JEKYLL_ENV=production`) and checked (`script/check-build.sh`, Lighthouse CI).

```
push ──► build job: jekyll build, check-build.sh, Lighthouse (mobile + desktop), upload _site
                      │  all green
                      ▼
         deploy job: download _site ──► wrangler pages deploy _site --project-name=… --branch=<branch>
                      │                                      │
                      │                    main ─────────────┴──► production (montedelgallo.com)
                      │                    any other branch ─────► preview   (<branch>.<project>.pages.dev)
                      ▼
         verify: Content-Security-Policy and X-Robots-Tag: noindex on the deployed *.pages.dev URL
```

`/_headers` (CSP, security headers, cache lifetimes) and `/_redirects` (the 301 map of the old
WordPress URLs) are part of `_site`, so Pages applies them without any dashboard setting. This folder
is not published (`deploy/` is in `exclude:` of `_config.yml`); the nginx fallback is in `deploy/nginx/`.

## 1. Create the Pages project (once)

Cloudflare dashboard, account of Monte del Gallo:

1. **Workers & Pages** → **Create** → **Pages** → **Upload assets** (this is the *Direct Upload*
   flow: it does not connect a Git repository). A project made this way cannot be switched to Git
   integration later, which is what we want.
2. Project name: `montedelgallo` (the workflow's default; to use another name set the GitHub
   repository variable `CLOUDFLARE_PAGES_PROJECT`). The project gets `montedelgallo.pages.dev`.
3. The dashboard asks for a first upload: upload any folder with an `index.html` (the real site
   replaces it with the first deploy from CI).
4. **Settings** → **Builds & deployments** → **Production branch**: `main`. Wrangler's `--branch=main`
   is then the production deployment; every other `--branch` is a preview.
5. **Settings** → **Functions**: nothing (the site is static). No build command, no environment variables.

### Custom domain

**Custom domains** → **Set up a custom domain** → `montedelgallo.com`, then `www.montedelgallo.com`
(the apex is the canonical address; `www` should redirect to it: **Rules** → **Redirect Rules** on the
zone, `www.montedelgallo.com/*` → `https://montedelgallo.com/${1}`, 301).

An apex domain on Pages needs the domain as a **Cloudflare zone** (nameservers at Cloudflare), so the
DNS of montedelgallo.com moves to Cloudflare. That is the heart of the cutover and is covered step
by step (including the mail records) in `tasks/launch-runbook.md`. Do not add the custom domain before
the runbook says so: it takes the domain over.

### Indexing and the `*.pages.dev` addresses

- **Previews** (`<branch>.montedelgallo.pages.dev`): Cloudflare sends `X-Robots-Tag: noindex` on every
  preview deployment by itself. Cloudflare's documentation: "By default, every preview deployment
  generated by Cloudflare Pages includes the `X-Robots-Tag: noindex` HTTP response header." Nothing to
  configure; the deploy job still checks the header on the URL it deployed.
- **The production alias and the per-deployment URLs** (`montedelgallo.pages.dev`,
  `<hash>.montedelgallo.pages.dev`) are not previews, so the site says it itself: `/_headers` has two
  host rules (`https://:project.pages.dev/*` and `https://:version.:project.pages.dev/*`) that add
  `X-Robots-Tag: noindex`. They match only `*.pages.dev`, never the custom domain. The canonical tags
  of every page already point to `https://montedelgallo.com`.
- Optional, after the launch: send the production `montedelgallo.pages.dev` address to the custom
  domain with an **account-level Bulk Redirect** (Cloudflare: "Disable access to `*.pages.dev`
  subdomain"), and put **Cloudflare Access** in front of the previews (**Settings** → **General** →
  **Enable access policy**: only the people in the account see previews; it protects previews only).
  A host-level redirect cannot be written in `_redirects` (it has no host matching), which is why the
  `noindex` header and the canonical tags are the baseline.

## 2. API token (Pages: Edit only)

**My Profile** (or **Manage Account**) → **API Tokens** → **Create Token** → **Create Custom Token**:

| Field | Value |
|---|---|
| Token name | `github-actions-montedelgallo-pages` |
| Permissions | **Account** → **Cloudflare Pages** → **Edit** (shown as *Pages: Edit*). Nothing else: no Zone, no DNS, no Workers. |
| Account Resources | Include → the Monte del Gallo account only |
| Client IP filtering / TTL | none (GitHub's runners have no fixed address); set an expiry (for example one year) and renew it |

Copy the token once (it is shown once). The **Account ID** is on the right of **Workers & Pages** →
**Overview** (a 32-character hex string).

## 3. GitHub secrets and environments

Repository → **Settings** → **Environments** → create **`production`** and **`preview`**. In *each* of
them add the two **environment secrets**:

| Secret | Value |
|---|---|
| `CLOUDFLARE_API_TOKEN` | the token of step 2 |
| `CLOUDFLARE_ACCOUNT_ID` | the account id |

Recommended protection: on `production`, **Deployment branches** → *Selected branches* → `main`
(the workflow already deploys production from `main` only; this makes GitHub enforce it) and, if the
client wants a second pair of eyes, **Required reviewers**. Never put a token in the repository, in the
workflow file or in a variable: `script/checks/deploy.rb` fails the build if a token-like value is
committed.

Optional repository **variable** (Settings → Secrets and variables → Actions → Variables):
`CLOUDFLARE_PAGES_PROJECT` if the Pages project is not called `montedelgallo`.

## 4. What the workflow does and does not do

- Runs on every push; a deploy happens only for pushes to a **branch** (not tags) and only after the
  `build` job (build, `script/check-build.sh`, both Lighthouse runs) has passed. Pull requests are not
  deployed on their own: the push of their branch already is (a pull request from a fork has no secrets).
- `concurrency` serialises deploys of one ref; a newer push to a *preview* branch cancels the older one,
  a production deploy is never cancelled.
- `permissions`: workflow `contents: read`; the deploy job adds `deployments: write` (the GitHub
  Deployments entry with the preview URL) and nothing else.
- The actions are pinned (`actions/*@vN`, `cloudflare/wrangler-action` by commit SHA with its version in
  a comment, wrangler by exact version); update them on purpose, not by accident.
- The job summary lists the deployment URL and the branch alias URL.

## 5. First deploy and checks

See `tasks/launch-runbook.md` (create the repository, push, add the secrets, open the pull request,
merge to `main`). After any deploy:

```bash
curl -sI https://<branch>.montedelgallo.pages.dev/ | grep -iE '^(HTTP|x-robots-tag|content-security-policy)'
script/smoke-redirects.sh https://<branch>.montedelgallo.pages.dev   # every old URL 301s, every page 200s
```

Roll back a bad production deploy from the dashboard (**Deployments** → an earlier production
deployment → **Rollback to this deployment**), or re-run the workflow of the last good commit.
